# ForgeDuet v0.3：补齐双向自动交接

## 结论

初版把自动交接写成可选项，导致构建方交付后停下、用户继续转述审查结果。这没有落实用户最初的要求。本次已修改两份 SKILL、共享协议、上手文档、模板和安装副本；不是只加一句“可以轮询”。尚待独立复核，不能把自测通过称为双方批准。

## 改动

1. 用户开始本机协作后，默认双向每 60 秒监控。构建方读 reviews/，审查方读 deliveries/。必须记录真实监控机制、任务 ID 或进程、游标和验证证据；每次交付后确认已重新等待，不让用户转述。
2. 区分本地脚本与真正唤醒：handoff.py 只检查文件，不调用模型。客户端要有实际调度器、后台任务完成通知或受信 CLI 适配器。Codex App 定时模型唤醒可能消耗额度，不能说零 token。没有能力时应尽早说明并明确选择后备流程，不能默认为人工交接。
3. 完整文件才触发：隐藏临时文件原子发布为正式 Markdown，拒绝覆盖旧报告；末尾有完成标记。只看文件大小稳定不够。标记也不等于内容真实，仍要核对完整 SHA、任务和证据。
4. 共享写入前拿 .lock/，记录唯一作者、原因、时间、token。兼容旧 mkdir 锁，不自动删除他人的锁。锁只跨短时发布/日志/获准 Git 操作，不跨测试、思考或等待；拿锁不产生额外权限。
5. updates.log 只追加；报告带作者和时区时间，允许修改的共享记录有更新表。提交后才记录真实最终 SHA，不编造自包含提交号。发布和日志是两次操作，崩溃窗口有明确限制和恢复要求。
6. 游标只在处理并留存结果后按哈希确认。脚本醒来不算消费消息；退出重启仍可读未处理内容。暂停/恢复保留基线，同 SHA 批准加明确接受后才闭环，不把旧任务的完成误当成新等待的停止条件。
7. 准备技能与开始项目严格区分。只改或安装 SKILL 时不得自行开启任何项目监控。本轮曾提前重启 WristFiles，用户澄清后已暂停；当前没有启动它的审查或本地轮询。后续必须等用户明确开始。
